# Design: async-rag-query

## Architecture Overview

Before this change, the only query path is synchronous:

```
Client ──POST /rag/query──► FastAPI Handler ──► RagQueryService.query() ──► LLM (10-30s) ──► 200 response
```

After this change, an async path runs alongside the sync path:

```
Client ──POST /rag/query/async──► FastAPI Handler
                                      │
                                      ├─ INSERT rag_query_jobs (status=pending)
                                      ├─ Queue.add("rag.query", jobData)
                                      └─ 202 { jobId, conversationId }

BullMQ ──rag.query:wait──► [Python Worker: query_worker.py]
                                 │
                                 ├─ RagQueryService.query()  (existing, unchanged)
                                 ├─ UPDATE rag_query_jobs (status=completed, result=...)
                                 └─ if webhook_url: POST result (fire-and-forget, 10s timeout)

Client ──GET /rag/query/jobs/:jobId──► FastAPI Handler ──► SELECT rag_query_jobs ──► status+result
```

## Database: `rag_query_jobs`

New table. Append-only from the HTTP layer; updated only by the worker.

```sql
CREATE TABLE rag_query_jobs (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id    UUID NOT NULL REFERENCES tenants(id),
    user_id      UUID NOT NULL REFERENCES users(id),
    status       VARCHAR NOT NULL DEFAULT 'pending',  -- pending|running|completed|failed
    request      JSONB NOT NULL,       -- full async request payload (for replay/audit)
    result       JSONB,                -- same shape as sync query response
    error        TEXT,
    webhook_url  TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at TIMESTAMPTZ
);

CREATE INDEX ix_rag_query_jobs_tenant_id ON rag_query_jobs (tenant_id);
CREATE INDEX ix_rag_query_jobs_status    ON rag_query_jobs (status);
```

**Design decisions:**
- `id` is the BullMQ job ID — we generate the UUID in the HTTP handler and pass it as the BullMQ job ID so the two are identical, avoiding a separate lookup table.
- `request` is stored as JSONB for audit trail and potential future replay.
- `webhook_url` is stored so the worker does not need the original request in memory.
- No `conversation_id` column — conversation_id is derived from `request->>'conversation_id'` or generated by `RagQueryService` and embedded in `result`.

## HTTP Interface

### `POST /rag/query/async`

**Request schema** (`AsyncRagQueryRequest`):

```python
class AsyncRagQueryRequest(BaseModel):
    message: str = Field(min_length=1, max_length=8192)
    knowledge_base_ids: list[str] = Field(min_length=1, max_length=20)
    conversation_id: str | None = None
    webhook_url: str | None = Field(default=None, max_length=2048)
    mode: Literal["grounded"] = "grounded"
    decomposition: dict[str, Any] | None = None
    planner: dict[str, Any] | None = None
    memory: dict[str, Any] | None = None

    @field_validator("webhook_url")
    @classmethod
    def webhook_must_be_https(cls, v: str | None) -> str | None:
        if v is not None and not v.startswith("https://"):
            raise ValueError("webhook_url must use https://")
        return v
```

**Response 202** (`AsyncRagQueryResponse`):

```python
class AsyncRagQueryResponse(BaseModel):
    jobId: str
    conversationId: str
```

**Handler logic:**
1. Generate `job_id = str(uuid4())` and `conversation_id` (use request value or generate new)
2. `INSERT rag_query_jobs` with `status=pending`
3. `Queue("rag.query", connection=redis_opts).add(job_id, job_data, {"jobId": job_id})`
4. Return `202 AsyncRagQueryResponse(jobId=job_id, conversationId=conversation_id)`

### `GET /rag/query/jobs/{job_id}`

**Response** (`RagQueryJobResponse`):

```python
class RagQueryJobResponse(BaseModel):
    jobId: str
    status: str  # pending|running|completed|failed
    result: dict[str, Any] | None
    error: str | None
    createdAt: str
    completedAt: str | None
```

**Handler logic:**
1. `repo.get_by_id_and_tenant(job_id, tenant_id)`
2. If `None` → raise `404`
3. Return `200 RagQueryJobResponse(...)`

**Security:** The repository query always filters by `tenant_id` — a job belonging to a different tenant is indistinguishable from a non-existent job (404).

## Worker: `query_worker.py`

New file: `apps/api/app/workers/query_worker.py`

```python
# Sketch — not final code

from bullmq import Worker, Job
import httpx

async def handle_rag_query(job: Job, token: str) -> None:
    data = job.data
    async with session_factory() as session:
        repo = SqlAlchemyRagQueryJobRepository(session)
        await repo.update_running(data["job_id"])

        try:
            result = await RagQueryService(session, settings).query(
                tenant_id=data["tenant_id"],
                user_id=data["user_id"],
                message=data["message"],
                knowledge_base_ids=data["knowledge_base_ids"],
                conversation_id=data["conversation_id"],
                # ... remaining fields
            )
            await repo.update_completed(data["job_id"], result)
            await _fire_webhook(data.get("webhook_url"), data["job_id"], "completed", result, None)
        except Exception as exc:
            await repo.update_failed(data["job_id"], str(exc))
            await _fire_webhook(data.get("webhook_url"), data["job_id"], "failed", None, str(exc))
            raise


async def _fire_webhook(url: str | None, job_id: str, status: str, result, error: str | None) -> None:
    if not url:
        return
    payload = {"jobId": job_id, "status": status, "result": result, "error": error}
    try:
        async with httpx.AsyncClient(timeout=10.0) as client:
            await client.post(url, json=payload)
    except Exception:
        pass  # fire-and-forget


def create_query_worker(settings, session_factory, redis_opts) -> Worker:
    return Worker("rag.query", handle_rag_query, {"connection": redis_opts, "concurrency": 10})
```

**Key design decisions:**

- `job_id` is generated by the HTTP handler and passed as the BullMQ job ID — the `rag_query_jobs.id` and BullMQ job ID are the same UUID, removing the need for a mapping table.
- Worker sets `status=running` on pickup, so polling clients can distinguish "queued" from "in-progress".
- `update_failed` is called inside the `except` block before re-raising — BullMQ will apply retry, but the DB row reflects the latest attempt's error immediately.
- Webhook is fire-and-forget: errors are silently swallowed and never affect job outcome.
- `httpx.AsyncClient` with `timeout=10.0` — no persistent connection pool needed since webhooks are rare.

## Retry Policy

```python
JOB_OPTIONS = {
    "attempts": 2,
    "backoff": {"type": "exponential", "delay": 3000},
}
```

Only 2 attempts (vs 3 for ingestion) because RAG queries are expensive (LLM tokens) and most failures are non-transient (bad knowledge base IDs, context overflow).

## Security Summary

| Concern | Mitigation |
|---|---|
| Cross-tenant job access | `get_by_id_and_tenant` always filters by `tenant_id`; returns `None` → 404 |
| Webhook to non-HTTPS | `field_validator` on `webhook_url` rejects any URL not starting with `https://` |
| Webhook SSRF | Caller must be authenticated; webhook is their own endpoint |
| Job data in BullMQ | Contains no secrets — only IDs and query text already held by the tenant |
